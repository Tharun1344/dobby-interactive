## 1. The "self-chat message every ~10 minutes"

**Not a scheduled task. It is the connect notice, re-fired by container restarts.**

Code path (`index.js`, `connection.update → open`): every successful connection sent a full status card to
the owner's self-chat, suppressed only when a notice had been sent in the previous 10 minutes
(`settings.lastConnectNotice`). A container that restarts more often than that therefore produced exactly
one message per 10-minute window — which is what the owner saw.

Restart evidence (Railway `deploymentLogs`, 2026-11-09):

| deployment | boot record |
|---|---|
| 16:34 | `previous run was KILLED WITHOUT WARNING after ~4 min … memory then 107 MB` |
| 16:28 | `… after ~51 min … 108 MB` |
| 15:36 | `… after ~4 min … 122 MB` |
| 15:32 | `… after ~6 min … 110 MB` |
| 15:26 | `… after ~3 min … 102 MB` |
| 15:20 | `… after ~5 min … 103 MB` |
| 15:17 | `… after ~3 min … 108 MB` |
| 15:13 | `… after ~2 min … 89 MB` |
| 15:12 | `… after ~30 min … 92 MB` |
| 14:41 | `… after ~36 min … 92 MB` |

Those timestamps match the deploy queue almost one-for-one (15:11–16:34 was a burst of deploys), so the
kills are **container replacements**, not a crash loop.

**Memory was not the cause** — Railway's own metrics for 14:00–18:30 UTC:

```
MEMORY_USAGE_GB: peak 0.2849 GB at 16:37   (samples 218, no zero gaps → no long outages)
CPU_USAGE:       peak 0.7999 at 16:36
```

Service settings: `restartPolicyType = ON_FAILURE`, `healthcheckPath = null`, `sleepApplication = false`
— so the platform health check cannot restart the app, and app sleeping is off. A "killed without
warning" is the expected shape of a deploy replacement (and of an OOM kill / segfault); peak memory
(285 MB) rules the OOM theory out for the observed window.

The old boot message claimed "almost always OUT OF MEMORY" — that wording is now evidence-based
(deploy/replacement, OOM or segfault) so the next investigation does not start from a wrong assumption.

### Fix

New module `lib/connectNotice.js` + `scripts/test-connect-notice.js` (10 checks, all passing):

* `CONNECT_NOTICE=first` (default) — announce once per pairing (`settings.noticeAnnouncedOnce`), then stay
  silent across restarts and reconnects.
* `CONNECT_NOTICE=always` — old behaviour, still floored at one notice per 10 minutes.
* `CONNECT_NOTICE=off` — never announce.
* Restart storms are reported **once per hour** (`settings.bootTimes`, `settings.lastRestartAlertAt`), as a
  single "container restarted N times in the last hour" line — the spam is not replaced by another spam.

Persistence: `noticeAnnouncedOnce`, `lastConnectNotice`, `bootTimes` and `lastRestartAlertAt` live in
`settings.json` (written atomically by `lib/settings.js`: tmp + rename) so a restart reads the decision
back. Proven by the test `first: the decision survives a restart through settings.json`, which writes and
re-reads a real file across three simulated boots.

## 2. Session persistence and restart recovery

* Auth is `useMultiFileAuthState(account.sessionPath)` on the Railway volume (`STORAGE_DIR=/data`,
  `auth_info_baileys/`) — session survives deploys; measured on the live service earlier in the day:
  `saved login: FOUND` after a redeploy.
* `creds.update → saveCreds` is wired, and `reconnectAttempts` is reset on a successful open.
* **Gap found:** `useMultiFileAuthState` rewrites `creds.json` in place, so a hard kill mid-write can leave
  invalid JSON and the next boot would ask for a new QR.
  **Fix (additive):** `protectSession()` restores a verified `creds.json.bak` when `creds.json` is missing or
  unparseable, and `backupSession()` refreshes that copy after every successful connection. Nothing is
  deleted and no credential is regenerated.
* Reconnect backoff was exponential but deterministic; **jitter (±25 %)** added on both paths so a platform
  blip cannot resynchronise every restart.
* Shutdown: `SIGTERM`/`SIGINT` → `server.close()` → `process.exit(0)` with an 8 s guard; session writes are
  already flushed by Baileys' per-update `saveCreds`.

## 8. Final verification (2026-11-09, after the fixes)

**Diff review — nothing removed that the bot needs.** Every deleted line in `git diff` is a line that was
replaced by its improved twin: the 10-minute quiet window → policy decision, two deterministic backoff
delays → jittered versions, the `===` token check → `tokenMatches`, `/health`'s `_req` signature + comment →
gated version, the "almost always OUT OF MEMORY" boot line → evidence-based wording. `index.js` shows
94 insertions / 12 deletions; no command, plugin, feature, config key or data file was dropped.

**Session backup/recovery — data-loss analysis.** `protectSession()` only ever copies *from* `creds.json.bak`
*into* `creds.json`, and only when the live file is missing or unparseable; a valid live session is never
overwritten by an older copy (a valid `creds.json` returns early). `backupSession()` refreshes the copy after
a successful connection. Neither function deletes anything, regenerates credentials or touches other session
files, and there is a single writer (one process, one socket) so no concurrent-write corruption path is
introduced. Failure mode when both files are bad is a warning plus a normal pairing prompt — the previous
behaviour, not a worse one.

**Secret scan.** Changed and new files contain no credentials, tokens or cookies — the only `creds` matches
are file *names* (`creds.json`), the Google/YouTube/Supabase values stay in `process.env`, cookies are read
from `YTDLP_COOKIES_B64` and written `0o600`, and the new tests use synthetic fixtures with no real numbers.

**Finding worth knowing:** `data/settings.json` is **tracked** by git (it predates this audit). It holds
runtime preferences (including any `.autoreply` text), and the repo is private, but it does not belong in
version control. `.gitignore` now lists it; untracking the copy already in history needs approval:

```bash
git rm --cached data/settings.json   # keeps the file on disk, stops tracking it (history still holds old copies)
```
